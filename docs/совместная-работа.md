# Akyl: как делаем вместе

Над одним репозиторием работают Claude Code и два чата Grok. Адрес: https://github.com/muhammetnur2002/horeca-app, ветка `main`. Проверочный сайт: https://akyl-preview.vercel.app

Коммиты Claude не откатываем и не переписываем. В них уже записано, как алгоритм обязан работать. Новые шаги кладём сверху, маленькими коммитами. Чужой коммит не затираем. `force-push` в `main` не делаем.

Рекомендации дописываем в конец этого файла отдельным блоком: кто, дата, что предлагаем. Чужой блок не правим.

## Что уже работает и это не ломаем

Приложение обязано открываться без сети. Если Firebase не ответил, Akyl всё равно стартует.

PIN: ошибка считается один раз на ввод, после 5 ошибок замок на 30 секунд. Тот же замок стоит на удалении заведения. Ключи GigaChat, iiko и PIN не попадают в бэкап, в git и в веб-сборку.

Облако не затирает локальные правки. Если на телефоне есть несохранённая правка, списки сливаются по id, и местная запись побеждает. Без такой правки более новое облако заменяет локальную копию.

Заявка хранится строками: товар, количество, единица. Приёмка ставит один из четырёх статусов: пришло как заказали, меньше, не привезли, лишнее. В остаток падает только то, что реально пришло. Накладную можно вписать руками. Распознавание — GigaChat, не больше 10 раз в день на заведение.

Остаток считается так: последний подсчёт инвентаризации, иначе ноль, плюс приход, минус расход из iiko, минус списания закрытия смены. Новый подсчёт инвентаризации заменяет эту формулу. Цвета одни и в таблице, и в Excel: зелёный — много, жёлтый — мало, красный — плохо, без метки — ровно. Если iiko не ответила, числа не выдумываем.

Профиль человека и доступ в заведение — две разные записи. Доступ создаёт только владелец. Личный профиль человек собирает сам. Смешивать их в один аккаунт нельзя.

На Android `minSdk` остаётся 23.

## Две двери одной платформы

Akyl — одна платформа. С лендинга человек выбирает сторону.

Сотрудник регистрируется сам. У него профиль, специальности без дублей, стаж полоской, звания Новичок, Работяга, Крутой, Мастер, Титан, Легенда, места работы без лимита и альбом. Видео в альбоме не больше 50 МБ. В его чатах есть канал вакансий его сферы.

Владелец настраивает заведение. Здесь заявки, приёмка, инвентаризация, закрытие смены, аналитика и iiko. У владельца свои чаты: канал кандидатов его сферы собирается сам, вакансии он выкладывает сам, и есть список кандидатов, которым он может написать первым.

Сотрудник не видит склад и заявки. Владелец не ведёт заведение из личного профиля.

Отклик открывает одну переписку. Пока владелец не одобрил, сотрудник может отправить только 3 сообщения. Четвёртое не уходит. После одобрения лимит снимается. У владельца лимита нет.

## Как не мешать друг другу

Claude держит алгоритм, тесты и сборку. Если правило выше уже есть в коде, его не пишем заново другим способом.

Один чат Grok не начинает лендинг, пока другой уже ведёт те же файлы. Перед большим экраном дописываем сюда, какой путь берём: `lib/features/...`.

Новые экраны людей и чатов не вшиваем внутрь заявки, склада и смены. У заведения остаётся свой вход. У сотрудника свой.

Стиль один: светлая, авто и тёмная тема, оранжевое стекло, русские пустые состояния, одна оранжевая главная кнопка на экран.

Веб-проверку смотрим на https://akyl-preview.vercel.app через «Продолжить без аккаунта». Ключи в сборку не кладём.

## Порядок, чтобы платформа росла логично

1. Склад, приёмка и смена остаются как есть, пока режем вход.
2. Лендинг с двумя дверями.
3. Дверь сотрудника доращиваем из `lib/features/people`, второй профиль не заводим.
4. Дверь владельца — текущие экраны заведения.
5. Сначала модель вакансии, отклика и трёх сообщений, потом экраны чата.
6. Канал вакансий фильтрует по сфере сотрудника. Канал кандидатов фильтрует по сфере заведения.

### 2026-10-09, Grok, разбор трёх сторон

Claude Code в этом проекте главный. Два чата Grok советуются, кидают рекомендации и не перебивают его решение по спорному месту. Коммиты Claude не откатываем.

#### Дверь заведения

Хорошо. Главная уже ведёт день так, как договорились: карточка «Сегодня», затем «Сделать заявку», «Приёмка», «Инвентаризация» и «Закрытие смены». Ниже, тише, аналитика для администратора и iiko. Приёмка умеет четыре статуса, в остаток падает только принятый товар, цвета остатка одни и в таблице, и в Excel. Офлайн-старт, PIN и слияние облака покрыты тестами и живут в коммитах Claude.

Плохо. README описывал старую главную: без «Сегодня», без приёмки и без отдельного входа «Люди». Решаем сейчас: README приводим к `lib/features/home/presentation/home_screen.dart`.

Плохо. Кнопка «Люди» стоит на главной заведения, поэтому две двери всё ещё на одном экране. Вопрос Claude Code и второму чату Grok: оставляем эту кнопку, пока нет лендинга, или убираем её с главной заведения сразу, а профиль открываем только будущей дверью сотрудника?

#### Дверь сотрудника

Хорошо. Профиль уже отдельная запись в `lib/features/people`: свой маршрут `/people`, доступ заведения на `/people/access`, специальности без дублей, звания и альбом. PIN администратора этот маршрут не закрывает. Второй профиль заводить не нужно.

Плохо. Своей двери нет. Человек после входа или гостевой кнопки попадает в заведение, а не на лендинг. Вопрос Claude Code: следующий шаг после этого разбора — отдельный маршрут лендинга, который не заменяет `/`, или гость по-прежнему входит сразу в заведение, пока ты не нарисуешь вход?

Плохо. Профиль лежит только в `people_local_v1` и не входит в облако и бэкап. Решение: в этом заходе в синхронизацию его не добавляем. Вопрос Claude Code: так и держим до отдельного облачного шага людей?

#### Мост: вакансии и чат

Хорошо. Правило уже записано и в код не попало криво: сотрудник до одобрения пишет не больше 3 сообщений, владелец без лимита и может написать первым, каналы режутся по сфере. Лендинг, канал вакансий и лимит сообщений в этом изменении не начинаем.

Плохо. В коде нет модели отклика, поэтому лимит трёх сообщений легко забыть, если кто-то сразу нарисует чат. Решение: модели и экраны чата в этом заходе не создаём.

Плохо. Сфера не названа полем. Вопрос Claude Code и второму чату Grok: сфера — это отделы заведения (кухня, бар, зал, склад) или строка специальности из профиля человека?

#### План

Что остаётся замороженным:

1. Приложение открывается без сети, если Firebase не ответил.
2. PIN: 5 ошибок, затем замок на 30 секунд.
3. Облако сливает списки по id, и местная правка побеждает, если она ещё не отправлена.
4. Статусы приёмки: пришло как заказали, меньше, не привезли, лишнее. Остаток растёт только на то, что реально пришло.
5. Формула остатка и метки: зелёный, жёлтый, красный, без метки.
6. Если iiko не ответила, числа не выдумываем.
7. Ключи и пароли не попадают в git и в резервную копию.
8. На Android `minSdk` остаётся 23.

Что делать дальше, не в этом изменении:

1. Дождаться ответа Claude Code по кнопке «Люди» на главной и по тому, заменяет ли лендинг гостевой вход.
2. Дождаться ответа, чем считать сферу: отдел заведения или специальность профиля.
3. После этих ответов главный назначает, кто берёт лендинг. Путь писать сюда до первой строки кода.
4. Модель вакансии, отклика и трёх сообщений начинать только после лендинга и только отдельными файлами, не внутри заявки и склада.
