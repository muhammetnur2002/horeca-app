# Бэкенд Akyl

База данных на PostgreSQL, совместимая с Supabase. Изоляция клиентов
обеспечивается средствами самой СУБД (Row Level Security), а не проверками
в коде приложения.

## Что уже сделано

Этап 1 плана: схема, разграничение доступа и проверки на них.
Синхронизация (этап 3) и аккаунты (этап 4) — следующие шаги.

## Требования

PostgreSQL 15 или новее, `psql` в PATH. Supabase для локальной разработки
не нужен: заглушка `local/00_auth_shim.sql` подменяет схему `auth`, поэтому
миграции работают на обычном PostgreSQL без изменений.

## Запуск

```powershell
cd supabase
.\run_local.ps1 -Seed
```

Пароль пользователя `postgres` скрипт спросит сам. Его можно передать и
параметром — это нужно для автоматизации:

```powershell
.\run_local.ps1 -Seed -Password ваш_пароль
```

Если раньше вы задавали `$env:PGPASSWORD` и он не подходит, скрипт скажет
об этом и спросит пароль заново. Сбросить переменную вручную:
`Remove-Item Env:PGPASSWORD`.

Скрипт рассчитан на Windows PowerShell 5.1 и сохранён в UTF-8 с BOM.
Без BOM PowerShell 5.1 читает файл в кодировке системы, и кириллица
ломает разбор строк. При правке сохраняйте кодировку и не используйте
конструкции PowerShell 6+.

```bash
cd supabase && ./run_local.sh --seed
```

Скрипт пересоздаёт базу `akyl_dev`, применяет миграции, разворачивает
демо-данные и прогоняет проверки доступа. Любая неудавшаяся проверка
останавливает выполнение.

## Структура

```
migrations/    миграции по порядку; на Supabase применяются как есть
local/         только для локальной разработки, на боевую базу не идут
tests/         проверки разграничения доступа
```

Имена файлов миграций — в формате Supabase CLI (`ГГГГММДДЧЧММСС_имя.sql`),
поэтому позже они подхватятся `supabase db push` без переименования.

## Принципы схемы

**Идентификаторы генерирует клиент.** Первичные ключи — UUID, созданные на
устройстве. Это позволяет заводить записи без сети и делает отправку
идемпотентной: повторная отправка той же смены гасится через
`on conflict (id) do nothing`.

**Деньги — целые в минорных единицах.** Все суммы хранятся в `bigint`
как тиыны. Ни `numeric`, ни тем более `float`.

**Удаление только мягкое.** Физическое удаление невозможно синхронизировать:
клиент, который был оффлайн, никогда не узнает об исчезнувшей строке.
Вместо этого проставляется `deleted_at`.

**Время ставит сервер.** `updated_at` проставляет триггер. Часы на устройствах
врут, и синхронизация по клиентскому времени тихо теряет записи.

**Два правила разрешения конфликтов.** Справочники (отделы, категории, товары,
сотрудники) — побеждает последний по `updated_at`. Операции (смены, заявки,
инвентаризации) — только добавление, версии никогда не сливаются.

## Разграничение доступа

| Роль      | Справочники | Операции         | Настройки заведения |
|-----------|-------------|------------------|---------------------|
| `owner`   | полный      | полный           | полный              |
| `manager` | полный      | полный           | полный              |
| `staff`   | чтение      | создание         | нет                 |

Сотрудник смены обязан уметь закрывать смены и оформлять заявки, но не может
менять справочники и править закрытые смены задним числом.

Функции проверок объявлены как `security definer` с явным `search_path`.
Это обязательно: политики на `memberships` обращаются к самой `memberships`,
и без обхода RLS получилась бы бесконечная рекурсия.

**Важно про UPDATE и DELETE.** Политика RLS не выбрасывает ошибку — она молча
отфильтровывает недоступные строки, и запрос завершается успехом с нулём
изменений. Проверки в `tests/` учитывают это и сравнивают число затронутых
строк, а не ждут исключения.

## Ключ iiko

`api_login` больше не хранится на устройствах. Он лежит зашифрованным в
`iiko_integrations`, право `select` на колонку с ключом не выдано никому
из клиентских ролей — даже `select *` по этой таблице завершится отказом.
Приложение читает состояние интеграции через представление `iiko_status`,
а записывает ключ через функцию `connect_iiko`, которая обратно его не отдаёт.

## Перенос на Supabase

```bash
supabase link --project-ref <ref>
supabase db push
```

`local/` не переносится. Пароль шифрования для `connect_iiko` хранится
в переменных окружения проекта, а не в коде.
